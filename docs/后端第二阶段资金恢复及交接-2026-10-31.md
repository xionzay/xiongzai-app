## 2. 根因与实现

### P1：先调用渠道再提交业务事务，无法可靠恢复

原退款批准／提现复核在数据库事务内执行 Provider。渠道成功接收但响应丢失或本地提交失败时，缺少持久执行意图，简单重试可能产生另一笔资金请求。

现在在原批准事务中写 financial_transfer_operations、scheduled_jobs 和 Outbox；金额使用 bigint 分，原退款／提现号和原渠道固定。渠道调用在事务外；收款账户仅调用前解密，Mock 结果只保留请求 HMAC，不保存明文账户或整个请求。

Mock 渠道结果放在独立 mock_transfer_results：它表示渠道已收到什么，不代表平台已完成记账。该结果不依赖 API／Scheduler 对象内存。

### P1：未知被当失败、重复发起或无期限悬挂

操作状态：

- READY：意图已提交，尚未执行。
- PROCESSING：已认领或渠道明确处于处理中。
- UNKNOWN：传输异常／渠道结果未知，不解锁、不记成功。
- MANUAL_REVIEW：自动恢复额度耗尽，仍不解锁。
- SUCCEEDED／FAILED：明确渠道终态，业务结果同事务落库。

每次认领递增 version、attempts，并生成独立 lease_token。预先安排 30 秒租约看门任务；查询间隔从 2 秒指数增长到最多 300 秒，默认 8 次执行预算。Scheduler 复用原文件生命周期轮询时机补投过期执行意图，避免任务自身失败重试耗尽后无人处理。

恢复优先查询；仅明确 NOT_FOUND 才以同一个操作 ID 补交。UNKNOWN、PROCESSING 不重发。人工 recover 也不是“再打一笔款”，只允许续查原操作；MANUAL_REVIEW 增加 8 次预算，不清零累计次数。执行中的有效租约拒绝人工并发接管。

终态业务写入、分录、收益分配、Outbox 和操作状态同事务；不修改历史分录。旧 lease_token／version 的迟到结果直接失效。查询与回调竞争只能完成一次记账。

### P1：退款状态提前表示已经发到渠道

依据 PRD V3.7“已发支付渠道才叫退款处理中”。退款批准先使用既有 SELLER_APPROVED（批准待执行），不提前产生 CHANNEL_REFUND_SUBMITTED／RefundProcessing。

确认渠道收到请求，或收到有效渠道回调后，再转 REFUND_PROCESSING 并更新支付状态。响应丢失时保持批准待确认提交；原售后冻结继续生效。管理员批准也复用该已有状态，来源仍由 admin_decision／seller_decision 区分，客户端不要仅凭枚举名断言是谁批准。

成功的同步 Mock 提交仍返回现有 REFUND_PROCESSING 响应；客户端必须始终采用服务端最新 version。未提交确认时不显示“已到账”，不开放重新申请以绕过恢复。

### P2：失败退款换事件 ID 重放

原退款只接受成功终态换事件重放。现增加匹配原渠道编号和原失败日志的失败重放确认，不重复恢复支付状态，不重复记账。明确失败经平台再次批准才创建新执行尝试；仍绑定原退款号、原支付渠道和批准金额。旧尝试迟到回调与新 provider_refund_no 不匹配时拒绝。

## 3. 迁移、兼容与回退

新增向前迁移：0017_supreme_blindfold.sql（已生成 Drizzle Schema、journal 和 snapshot）。

- financial_transfer_operations：外键绑定退款或提现；必须且只能绑定对应业务；正整数分金额；受限渠道和状态；同业务仅一条活跃尝试。
- mock_transfer_results：按 kind + channel + idempotency_key 唯一；仅保存请求 HMAC、模拟渠道编号、结果和版本。
- 不修改旧表、旧迁移、历史分录，不增加真实渠道、银行卡或新的外部依赖。
- 全量隔离 Schema 应用 18 项迁移后为 74 张表、70 个枚举；本轮新增 2 张表、没有增加 Enum。

迁移前已在处理的记录没有可靠“渠道未收到”证明，因此不自动补造成 READY、更不以新操作 ID 重发。原回调路径继续兼容无意图记录。此类历史记录需按原渠道编号通过既有对账／本地已知 Mock 回调处置；自动历史接管不在本次完成清单。

应用回退：先停止认领新的恢复任务（与运行服务负责人约定窗口），保存新增表及已发请求，不删除迁移、不把 UNKNOWN 改 FAILED、不释放未明资金。旧版本不理解新恢复任务；回退后需按原编号对账处理，不运行旧批准路径重发。这是保留数据的应用回退方案，不提供破坏性 down migration。

本轮未自动迁移共享 public。只读状态：开发库 17/18，专用测试库 public 5/18。集成测试在随机 Schema 内完整应用全部迁移，与 public 历史迁移数量无关。

## 4. 新增管理 API

全部保留管理员 Session、MFA、RBAC。统一错误结构不变。

| --- | --- | --- |

两个写接口在 production 拒绝，且生产原有 Mock 配置启动拒绝仍保留。无真实支付配置新增。


## 5. 客户端交接

- 用户端／App：以退款实际 status、服务端金额与最新 version 为准；SELLER_APPROVED 在此表示批准待执行，可能来自管理员；不是已到账，不允许用户自行重发退款。UNKNOWN／待人工不等于明确失败。
- 管理后台：新增恢复管理接口尚未做页面；待人工应说明资金仍冻结，操作需要原因、权限及 MFA；查询原单，不新建提现。活跃列表上限 100，进一步检索分页未在本轮增加，已知执行 ID 可用详情查询。
- Mock 结果控件只能作为本地工具，展示“模拟渠道结果，未直接完成平台业务”，之后读取真实业务结果。不得自动确认或伪造退款／提现成功。
- 历史无执行意图的资金单不能进入此自动补交逻辑，需单独对账。
- 售后完整能力声明未扩大，remedy_fulfillment、negotiated_receipt_clock、automatic_liability_ruling 仍为 false；客户端不能提前展示可执行新售后操作。
- Web Cookie、App Bearer、后台认证及手机号换绑／导出／注销真实状态未改变。
