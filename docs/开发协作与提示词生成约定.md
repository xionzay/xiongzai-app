# 开发协作与提示词生成约定

建立日期：2026-09-06。

用户希望后续每一步先由当前协作任务理解项目现状、判断依赖和开发顺序，再生成可直接交给相应开发任务执行的提示词。范围包括原生用户端、浏览器用户端、后端、数据库、管理后台、文件与消息、官网、测试、部署和上架准备。

## 生成提示词前先核实进度

1. 阅读用户最新要求，确认本轮目标和已明确的范围；区分询问、要求生成提示词与要求直接实施。
2. 核对完整项目资料清单：现行 PRD、商业规则、架构、模块说明、验收报告、视觉说明，以及可访问的相关任务记录。历史版本按适用范围和明确修订关系使用，不只按版本号或文件日期判断。
3. 以当前工作区源码为工程事实，核对分支、提交、未提交和新增文件。项目存在并行任务，不能只查看最近提交，也不能把另一个任务的计划当成已经写入的代码。
4. 复用已有全文阅读记录前核对文件是否变化；新增、修改或之前未覆盖的业务资料和源码必须补读。涉及跨模块或全局改变时，重新核对完整相关链路。精确相同内容可复用阅读记录，不能用关键词搜索或自动摘要代替新内容阅读。
5. 明确区分：计划、已有页面、已接接口、已有后端逻辑、历史验证、本轮验证、真实渠道接入和正式上线。任何报告中写“完成”都需要核对其实际覆盖范围。
6. 无法访问、未提供、返回空内容或未验证的信息应明确标注，不声称知道。外部平台规则、资质和接口要求在实际使用前核对当前官方来源。

资料入口为[项目开发现状总览](/Applications/c2c游戏服务软件/output/project-audit-2026-09-06/README.md)及[阅读覆盖清单](/Applications/c2c游戏服务软件/output/project-audit-2026-09-06/coverage.md)。它们是 2026-09-06 的静态快照，后续必须核对变化，不能永久沿用其中的完成状态或缺口。

## 每次向用户交付什么

先用简明语言说明当前做到哪里、本步解决什么、为什么此时做，以及影响哪些模块。然后给出一份可直接复制的完整提示词，不要求用户自行拼接零散指令。

每份执行提示词应包含：

- 项目路径、当前代码和资料基线，执行前需要阅读的具体文件。
- 本步目标、业务流程、明确的完成标准。
- 已实现且应复用的能力，实际缺口，以及需要处理的接口、状态和权限。
- 涉及的原生 App、Web、后端、数据库、后台、文件、通知等范围；纯 UI 改动按真实影响限定范围。
- 前置依赖和跨模块约定；存在接口变化时，说明生产方和使用方如何一起适配。
- 适用的验证：页面和交互、业务结果、数据一致性、权限、错误恢复。测试强度与改动风险相称，纯样式改动不强制跑全部系统测试。
- 最终回报格式：修改文件、完成行为、执行的验证及结果、未验证项、遗留依赖，以及下一步建议。

提示词必须自包含，不能仅写“按之前说的做”。实际开发任务可访问的文件和上下文可能不同，应给出足够明确的路径和业务约定。

## 如何安排多个模块

按实际依赖安排，避免固定套用“所有功能都先改数据库”的顺序：

- 纯 UI：主要修改对应界面、组件和素材，并检查显示与操作。
- 已有接口的新页面：优先复用接口，补导航、权限和各种界面状态。
- 新数据或新业务：先统一业务和接口约定，再按需要完成数据库、后端、用户端和后台的适配。
- 文件或聊天：同时考虑消息结构、资源归属、访问权限、保存和删除、审核、发送与接收恢复。
- 订单和资金：核对订单、退款、账务、定时任务、通知及后台处理的完整链路。
- 官网和 IP：根据用户确定的优先级并行推进，素材完成不等于产品接入完成。

用户要求分步时，先给当前可以执行的一步及后续依赖，不把所有模块拆成互相矛盾的独立提示词，也不提前锁死后续实现。

## 一步完成后如何继续

读取实际代码变化、执行记录和结果，确认完成条件，再更新后续顺序。用户提供其他任务的总结时，可以作为线索，但可访问源码时应继续交叉核对；没有执行证据的测试只记录为未验证。

如果用户只要求生成提示词，本轮交付提示词，不因此自动修改业务代码、创建任务或向其他任务发送执行消息。用户明确要求当前任务直接实施时，再在授权范围内实施。

该文件用于恢复协作方式，不承诺跨任务自动获得全部历史记忆。新任务可以通过本文件、现状总览和当前工作区重新建立上下文。
