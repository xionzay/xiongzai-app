## 1. 实现范围

本模块基于既有 PostgreSQL 表实现，不新增迁移：`refunds`、`refund_logs`、`complaints`、`complaint_evidences`、`complaint_logs`、`reviews`、`rating_aggregates`，并复用 `orders`、`payments`、`files`、`file_usages`、`admin_operation_logs`、`outbox_events`、`inbox_events`、`idempotency_keys`。

金额始终使用 bigint 分，并以十进制字符串通过 HTTP 传输。退款、投诉的核心写入使用行锁与 `status + version` Compare-And-Set。退款日志、投诉日志和管理员审计只追加，不提供修改或删除接口。

## 2. 状态机

### 2.1 退款

```text
REQUESTED
  ├─ 陪玩同意 → SELLER_APPROVED → REFUND_PROCESSING → REFUNDED
  └─ 陪玩拒绝 → SELLER_REJECTED → 平台介入 → PLATFORM_REVIEW
PLATFORM_REVIEW / SELLER_REJECTED / NEGOTIATING
  ├─ 平台同意 → REFUND_PROCESSING → REFUNDED
  └─ 平台驳回 → REJECTED
REFUND_PROCESSING ─ 渠道失败 → PLATFORM_REVIEW
```

同一订单可以存在多条已结束的部分退款，但部分唯一索引保证同一时刻最多一条有效退款。渠道成功回调在同一事务内锁定退款、订单和支付，原子累加退款金额；任何累计值不得超过订单实付或支付金额。`inbox_events` 以渠道事件 ID 防止重复回调二次入账。

### 2.2 投诉

```text
SUBMITTED → ACCEPTED → PROCESSING → COMPLETED
                         ├─ NEED_MORE_EVIDENCE → PROCESSING
                         └─ CLOSED
```

用户可以在结案前补充已验证且归本人所有的文件。证据关联同时写入 `complaint_evidences` 和 `file_usages`。客服/管理员的受理、调查、要求补证、完成和关闭都写投诉日志、管理员审计和 Outbox。

### 2.3 评价

完成订单只能创建一条评价。数据库订单唯一约束不会因评价被隐藏而释放，因此不能二次评价。首期不提供编辑接口。后台可以在 `PUBLIC` 与 `HIDDEN` 间隐藏或恢复；每次操作均在事务中锁定评分主体，重新计算陪玩和商品的 `rating_aggregates` 及展示冗余字段。

## 3. HTTP 接口

### 用户与陪玩

- `POST /api/v1/refunds`：发起退款，要求 `Idempotency-Key`
- `GET /api/v1/refunds`、`GET /api/v1/refunds/:refundId`
- `POST /api/v1/refunds/:refundId/escalate`：申请平台介入
- `GET /api/v1/seller/refunds`、`GET /api/v1/seller/refunds/:refundId`
- `POST /api/v1/seller/refunds/:refundId/decision`
- `POST /api/v1/complaints`、`GET /api/v1/complaints`、`GET /api/v1/complaints/:complaintId`
- `POST /api/v1/complaints/:complaintId/evidences`
- `POST /api/v1/reviews`、`GET /api/v1/reviews/me`
- `GET /api/v1/products/:productId/reviews`

### 管理后台与渠道

- `GET /admin-api/v1/refunds`、`GET /admin-api/v1/refunds/:refundId`
- `POST /admin-api/v1/refunds/:refundId/decision`
- `GET /admin-api/v1/complaints`、`GET /admin-api/v1/complaints/:complaintId`
- `POST /admin-api/v1/complaints/:complaintId/actions`
- `GET /admin-api/v1/reviews`
- `POST /admin-api/v1/reviews/:reviewId/moderation`
- `POST /callbacks/v1/refunds/WECHAT_APP` / `ALIPAY_APP`：按原支付渠道处理签名回调
- `POST /callbacks/v1/refunds/mock`：仅 development/test 保留的兼容入口，生产和预发拒绝

后台接口要求管理员会话、MFA 和对应 `refund.*`、`complaint.*`、`review.*` RBAC 权限。

## 4. 事务与一致性边界

- 发起退款：幂等占位、退款记录、订单售后状态、退款日志和 Outbox 同事务提交。
- 陪玩/平台处理：退款 CAS、支付状态、日志、审计和 Outbox 同事务提交；渠道创建退款使用不可猜测退款号作为幂等键，Provider 必须由关联支付单的 `payments.channel` 选择。
- 退款回调：Inbox 去重、退款完成、订单/支付累计退款、日志和 Outbox 同事务提交。
- 投诉动作：投诉 CAS、不可变日志、管理员审计和 Outbox 同事务提交。
- 评价创建/治理：评价状态、两类评分聚合、商品/陪玩展示评分、管理员审计和 Outbox 同事务提交。

## 5. UI 接入

用户端退款申请与详情、投诉提交与详情、评价提交与列表已连接真实 API；陪玩端退款处理连接卖家退款接口；管理后台退款、投诉、评价列表和治理操作连接管理 API。保留既有视觉样式，不实现优惠券、评价编辑或生产支付渠道。

## 6. 测试覆盖

真实 PostgreSQL 集成测试覆盖：两次历史部分退款、并发退款、超额退款、重复渠道回调、投诉证据和完整状态流转、日志不可修改、评价订单唯一、1–5 分校验、隐藏/恢复评分重算和管理员审计。

## 2026-10-31：退款批准、提交与未知恢复

依据最新 PRD“已发渠道才称退款处理中”：批准先写持久执行意图并保留 SELLER_APPROVED（批准待执行）；管理员批准也复用该既有状态，批准来源由 admin_decision／seller_decision 判断。服务端确认渠道收到请求或收到有效回调后才写 REFUND_PROCESSING、支付 REFUNDING、CHANNEL_REFUND_SUBMITTED 和 RefundProcessing 事件。

传输错误是 UNKNOWN，不是退款失败。原售后冻结保持；仅明确失败回到 PLATFORM_REVIEW，不产生实际退款、不解除售后；明确成功才更新累计退款、账务和免佣／欠款事实。失败换事件 ID 回放幂等，矛盾终态拒绝。失败后平台批准可建立新尝试，仍使用原支付渠道；旧尝试回调不能覆盖新尝试。

调用在事务外，恢复、审计、Mock 管理 API、迁移及测试证据见 [资金恢复交接](后端第二阶段资金恢复及交接-2026-10-31.md)。原回调兼容历史无执行意图记录，但不自动凭空重发此类请求。完整 V3.1 两轮协商、补充履约、裁决／申诉、特殊受理及评价图片未因此实现，能力声明不提前开放。
