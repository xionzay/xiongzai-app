## 实际修复

1. 原 commerce E2E 的新案件仍走旧卖家退款 decision：按实际新规则识别创建 `/after-sale/cases`，详情存在 `case_id` 时进入案件动作。旧无案件退款仍保留旧路径，`CASE_ACTION_REQUIRED` 未删除。
2. 卖家订单列表摘要没有完整案件/操作字段：点击后读取服务端订单详情，再决定页面操作，不用摘要推断能力。
3. 评价图片选择器可能选到之前已绑定另一评价的图片，后端正确返回冲突：`GET /me/files` 增加 `bound_review_id`；Web 只选明确未绑定且已校验、人工审核通过的文件。服务端原绑定检查保留。
4. 图片 content_path 在本地 Web 可能指向前端端口：提取原 API 地址解析器，图片与 Cookie API 使用同一解析规则；拒绝任意图片 URL。
5. 后台已有隐私确认动作却没有能力声明：仅在有未共享证据时返回 `MARK_EVIDENCE_SHAREABLE`。选择文件及“敏感信息已遮挡”均需独立手动确认，默认不勾选，后端仍校验显式 true。
6. 后台案件文件详情原链接不存在：改用已有 `/files/:id/access` 元数据入口，详情预览复用现有授权预览，不将签名链接写入公共展示。
7. 独立 Web 案件页补充读取订单实付与补充履约凭证，筛选本案 `remedy_evidence_file_ids`；App 同样通过订单 access API 预览。不解除冻结，不用普通确认绕过补充履约验收。
8. 操作已成功但后续历史/列表刷新失败，不再提示业务操作失败；明确成功与刷新失败，防止误重提。
9. API 地址解析器提取后，12 条会话回归的测试加载器仍寻找旧内联函数。改为加载真实新模块，原 401/并发轮换/拒绝写重放断言全部保留。
10. 浏览器入驻测试按当前已有“我的→设置→切换身份→申请入驻”入口操作；未跳过资质守卫。退款批准后先断言 F01，再发送仅 Node 测试进程持有签名材料的 Mock 回调，不能将批准当到账。

## 三端交接

- Web/RN 买卖家动作：MODIFY/WITHDRAW/APPROVE/REJECT/OFFER/RESPOND/ESCALATE/ADD_EVIDENCE/SUBMIT_REMEDY/APPEND_REMEDY/CONFIRM_REMEDY/EXTEND_REMEDY/ACCEPT_DECISION/APPEAL，仅按服务器 `available_actions` 展示。列表和历史分页，不凭枚举开放能力。
- 方案必须显式接受/拒绝；裁决显示具体 ID、事实、依据、责任、金额、理由、剩余义务、执行条件与期限。单方接受不表示执行完成。
- 补充履约仍在原案件，至少五截图及 20000 分录屏门槛；文件上传、校验、人工审核、案件核查分别展示。正常/补充验收共享一次 24 小时延期，服务端绝对时间为准。
- 后台保留现有案件管理基础，补齐特殊受理和独立隐私确认；需人工核验首次联系时间和严重问题。主管、初判/复核分离、操作原因及金额门槛由后端最终决定。
- 资金只展示服务端字符串：`funding.held_cent`、`commission_reserved_cent`、`funding_gap_cent`，财务摘要 `after_sale_held_cent`、`pending_recovery_cent`。使用 BigInt 安全格式化，不重新计算财务事实。
- `EXECUTION_PENDING` 不等于 F01；F01 不等于实际退款成功。特殊资金不足整笔待执行，足额后原渠道退款，不拆分、不垫付。RECHECK_FUNDING 与 RETRY_REFUND 按服务器能力区分，未知结果不能重发。
- D06/D09/D13 为已获授权的临时本地配置，正式启用前确认。图片数量/MIME/大小来自 `/files/policies`，不是客户端自定正式规则。
- 案件材料使用 `/files/after-sale-evidence/:case/:file/access`，补充履约用 `/files/order-evidence/:order/:file/access`，短时授权只留内存，后台/离页清理；未完成独立隐私确认的对方原始材料仍拒绝访问。
- ui-ux-pro-max 用于确认、加载/错误反馈、可见标签与无默认敏感确认的检查；没有借此重做现有视觉。原生触摸、读屏和设备布局仍需人工验收。
