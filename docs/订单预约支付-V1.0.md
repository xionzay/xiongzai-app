# 熊崽电竞订单、预约与支付实现说明 V1.0

> 2026-10-10：下文预约/接单和 ACTIVE 超时费率配置主要适用于旧链路。四游戏新商品创建的订单使用明确 `rule_version=V3.1` 与 `fulfillment_seconds` 快照，固定正常收货 72 小时、正常成交 10% 服务费，不调用旧接单逻辑。完整接口及验证结果见《第一阶段商品与新订单整改及客户端交接-V1.0》。

## 第一阶段非预约订单

`PENDING_PAYMENT → PENDING_SERVICE → IN_SERVICE → PENDING_BUYER_CONFIRM → COMPLETED`。

- 新订单只需商品、数量及多规格时的 SKU；拒绝预约字段和非空买家备注。服务端保存商品、SKU、价格、游戏、完成期限和交易/退款协议权威快照；创建时明确规则版本。
- 区分条件：`rule_version=V3.1 AND fulfillment_seconds_snapshot IS NOT NULL`。已有只标 V3.1 但仍含预约时间的订单不被自动重解释；旧商品新建预约单明确保存 `legacy`。
- 新单不写预约占用、不安排接单超时，`accept/reject` 返回 `ORDER_ACTION_NOT_SUPPORTED`。支付成功进入待服务，开始履约不重置支付起算的完成期限。
- 创建、支付检查双方正常用户、有效人工实名且成年、店铺与商品可交易、当前本地交易协议接受记录。客户端不得自行提供权威金额；`expected_payable_amount_cent` 可用于发现预览后价格变化。
- 微信/支付宝均按现有路由使用 Mock，渠道写入支付记录；回调、查询、重试记录和退款保持各自原渠道；生产配置拒绝 Mock。
- `seller/orders/:id/complete` 接受 `version,evidence_file_ids`。至少 5 张唯一的私有履约截图；实付 `>=20000` 分需连续录屏，MP4 视频轨与时长校验、人工审核员显式确认连续性后可提交。只验格式不能自动判定交付真实。相同文件及相同字节不同文件 ID 不可跨订单复用。
- 凭证使用 `ORDER_FULFILLMENT_IMAGE/VIDEO`，绑定 `ORDER/EVIDENCE`；记录只能追加不能覆盖。双方通过 `/api/v1/files/order-evidence/:orderId/:fileId/access` 取得运行时短链接；不公开对象键。
- `orders/:id/extend-receipt` 一单一次 +24h，数据库防止额度重置；未来补充履约必须复用同一字段。`orders/:id/remind` 在待服务/履约中每 24h 一次。
- 72h 自动确认、剩余 24/2h 提醒都使用绝对截止时间和当前订单 version；延期或售后恢复会重排任务，旧任务失效。履约逾期仅提醒双方，不伪造自动退款或判责。
- 售后处理中、退款中或证据核查中不能普通确认/自动结算。平台最终驳回本地基础退款恢复计时，新单至少保留 24h 收货，不返还已用延期额度。
- 正常零退款服务费 `(实付分*1000+5000)/10000` bigint 四舍五入，重复确认只生成一次收益；实际退款延续原有整单免服务费与追加冲正逻辑。
- 未完成补充履约、协商改钟、自动判责等复杂 V3.1 售后；详情的 `after_sale_capabilities` 明确返回未开放能力，客户端不可伪造成功，不存在的操作路径返回统一 404。

## 1. 实现范围

本阶段实现单 SKU 订单预览与创建、预约占用、支付单、支付回调、订单状态流转、超时任务以及买家/陪玩端现有页面的数据接入。订单金额使用 bigint 分，`discount_cent` 永远为 0，不包含优惠券逻辑。

生产超时与费率不写死在表结构或业务代码中。下列配置必须以 `platform_configs` 的 ACTIVE 版本启用：

- `order.payment_timeout_seconds`
- `order.accept_timeout_seconds`
- `order.auto_confirm_seconds`
- `finance.commission_rate_bps`

## 2. 用户端接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/orders/preview` | 校验商品、SKU、陪玩、可用时间并计算金额 |
| POST | `/api/v1/orders` | 使用 `Idempotency-Key` 创建订单和预约占用；原生 App 同时提交 `expected_payable_amount_cent` 防止预览后价格被静默变更 |
| GET | `/api/v1/orders` | 买家订单游标分页 |
| GET | `/api/v1/orders/:orderId` | 买家或关联陪玩查看订单详情、支付和状态日志 |
| POST | `/api/v1/orders/:orderId/cancel` | 买家取消待付款订单 |
| POST | `/api/v1/orders/:orderId/confirm` | 买家确认服务完成 |
| GET | `/api/v1/companions/:sellerId/availability` | 查询陪玩未来开放的可预约区间 |

## 4. 支付接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/payments` | 使用 `Idempotency-Key` 创建支付单；必须提交 `payment_channel: WECHAT_APP | ALIPAY_APP` |
| GET | `/api/v1/payments/:paymentId` | 查询支付状态 |
| POST | `/api/v1/payments/:paymentId/query` | 按支付单已保存的原渠道主动查询 Provider |
| POST | `/callbacks/v1/payments/WECHAT_APP` | 微信 App 支付回调；本地由独立 Mock Provider 处理 |
| POST | `/callbacks/v1/payments/ALIPAY_APP` | 支付宝 App 支付回调；本地由独立 Mock Provider 处理 |
| POST | `/callbacks/v1/payments/mock` | 仅供 development/test 的兼容回调，按支付单反查原渠道 |
| POST | `/api/v1/payments/:paymentId/mock-confirm` | 仅非生产 Mock 模式可用的测试支付确认 |

支付 Provider Router 以 `WECHAT_APP` / `ALIPAY_APP` 为闭集路由。创建、幂等重放、主动查询、成功/失败回调、超时关闭和退款始终使用 `payments.channel` 中的原渠道。同一幂等键改变订单或渠道会返回 `PAYMENT_IDEMPOTENCY_CONFLICT`。本地两个渠道均是 Mock，但不会把数据库渠道写成 `MOCK`。生产、预发环境禁止 Mock Provider 和 `/mock` 回调。

## 5. 事务边界

创建订单在一个数据库事务中完成：幂等键占位、订单快照、预约占用、初始状态日志、付款超时任务、Outbox 事件和幂等响应。任一步失败全部回滚。`order_slot_reservations` 的 GiST 排斥约束是最终并发保护，同一陪玩的有效预约不能重叠。

支付成功回调在一个数据库事务中完成：支付事件去重、支付单 CAS、订单 CAS、预约 HELD 转 CONFIRMED、接单超时任务、订单日志和 Outbox。支付渠道调用本身不放在长事务中。

取消、接单、拒单、开始、完成和买家确认均锁定订单，并使用 `id + current_status + version` 更新。状态日志和 Outbox 与业务状态同事务提交。取消、拒单、付款超时、接单超时和最终完成都会释放预约。

## 6. 定时任务

- `ORDER_PAYMENT_TIMEOUT`：待付款订单到期后关闭订单与未完成支付单，并释放预约。
- `ORDER_ACCEPT_TIMEOUT`：已支付但陪玩未接单时关闭订单并释放预约；后续退款阶段消费该事件创建退款流程。
- `ORDER_AUTO_CONFIRM`：陪玩提交完成且买家超时未确认时自动完成订单并释放预约。

Scheduler 通过 `scheduled_jobs` 竞争领取任务，业务处理器本身可重复调用；状态 CAS 保证重复执行不产生第二次状态变化、日志或 Outbox。

## 7. UI 接入

用户端沿用原视觉样式，服务详情把真实商品与 SKU 传入规格页；预约页读取开放时间；确认订单页先预览再幂等创建；收银台使用 Mock Provider 完成开发支付；订单列表和详情读取真实订单。陪玩订单页读取真实订单，并将接单、开始和完成按钮连接到真实状态机接口。

当数据库没有真实业务数据时，现有展示数据仍保留为页面空环境预览，不会被提交到生产数据库。

## 8. 原生 App 阶段 3 接入

原生 App 已接入真实可约时段、订单预览、幂等创建、订单详情、支付创建、支付查询和非生产 Mock 确认。订单与支付 Idempotency-Key、订单 ID 和支付 ID 存入系统 Keychain/Keystore，用于网络超时、页面恢复和冷启动恢复；不保存支付渠道凭证。

创建订单前 App 会重新请求预览并携带 `expected_payable_amount_cent`。服务端在创建事务内重新计算，金额不同则返回 `409 ORDER_PRICE_CHANGED`，整个事务回滚，不创建订单、预约占用或幂等结果。

支付处理中采用有限退避轮询，并在 App 回到前台时重新查询服务端。客户端深链和支付渠道返回值不能覆盖服务端 `payments` 与 `orders` 状态。
