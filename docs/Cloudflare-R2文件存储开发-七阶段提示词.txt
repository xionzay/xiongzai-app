Cloudflare R2 文件存储开发——七阶段提示词

使用说明：
1. 按阶段 1 → 阶段 7 的顺序使用。
2. 每次只复制一个阶段，等待该阶段完成、测试通过并给出报告后，再发送下一阶段。
3. 不要在多个任务中同时发送不同阶段，避免并发修改相同代码。

======================================================================
阶段 1：现状审计与接入准备
======================================================================

现在执行“文件存储阶段 1：Cloudflare R2 接入前审计与准备”。

项目根目录：
/Applications/c2c游戏服务软件

开始前阅读：

- docs/文件存储-V1.0.md
- docs/熊崽电竞-技术架构设计-V1.0.md
- docs/数据库设计-V1.0.md
- PRD 中“文件与对象存储设计”
- apps/api/src/file-storage.service.ts
- apps/api/src/file-storage.controllers.ts
- apps/api/src/object-storage-provider.ts
- apps/api/src/file-inspector.ts
- apps/api/src/config.ts
- apps/mobile 中媒体上传相关代码

本阶段只做本地代码审计和准备，不创建任何 Cloudflare 资源，不修改外部账号，不购买服务。

任务：

1. 检查当前文件存储实现是否完整符合 PRD。
2. 检查 S3 SigV4 签名是否兼容 Cloudflare R2。
3. 检查上传 URL、下载 URL、Bucket 路由和 object_key 设计。
4. 检查 SHA-256、大小、MIME、图片尺寸、音频时长校验。
5. 检查所有权、用途隔离、公开/私有访问和管理员审核。
6. 检查配置是否支持开发、测试和生产环境分离。
7. 检查密钥是否可能进入 Git、日志或 App。
8. 整理真实 R2 联调需要的资源和配置清单。
9. 补齐无需外部账号即可完成的代码、测试和文档。
10. 运行 API 类型检查、文件存储测试和相关业务回归。

必须保留现有未提交修改，不能创建生产资源，不能伪造真实 R2 联调结果。

完成后报告：

- 修改文件
- 测试结果
- 已确认的 R2 兼容性
- 发现的问题及修复
- 下一阶段需要创建的准确外部资源
- 需要我授权的操作

完成本阶段后停止，不自动进入阶段 2。

阶段 2：创建开发环境 R2 资源
======================================================================

现在执行“文件存储阶段 2：Cloudflare R2 开发资源创建”。

项目根目录：
/Applications/c2c游戏服务软件

先读取 docs/文件存储-V1.0.md 和阶段 1 的审计结果。

本阶段只允许处理开发环境，不得创建、修改或接触生产资源。

计划创建：

1. 开发公开媒体 Bucket：
   xiongzai-dev-public-media

2. 开发私有媒体 Bucket：
   xiongzai-dev-private-media

3. 一个最小权限 R2 API Token：
   - 只允许操作上述两个开发 Bucket
   - 只授予文件读取、写入、删除所需权限
   - 不使用 Cloudflare Global API Key
   - 不授予无关账号级权限

4. 开发 Bucket CORS：
   - 仅允许明确的开发 Origin
   - 允许 PUT、GET、HEAD
   - 允许 Content-Type
   - 允许 x-amz-meta-sha256
   - 允许 x-amz-meta-size-bytes
   - 暴露 ETag、Content-Length、Content-Type

安全要求：

- 在执行任何外部操作前，先向我列出资源、费用可能性、权限和回滚方式，并等待明确授权。
- 密钥只能写入 Git 忽略的本地环境文件或密钥管理系统。
- 不在回复、日志或测试输出中显示 Secret Access Key。
- 不开启私有 Bucket 匿名访问。
- 不绑定生产域名。
- 不上传真实用户文件。
- 不购买任何付费服务。
- 如果缺少 Cloudflare 登录状态、权限或计费授权，停止并说明，不绕过权限。

创建后使用无隐私测试文件验证：

- Bucket 存在
- Token 权限足够但不过度
- 私有 Bucket 无法匿名访问
- CORS 配置正确
- 可以精确删除测试对象

完成后报告创建的资源、配置结果、费用说明和回滚方式，然后停止，不自动进入阶段 3。

阶段 3：后端真实 R2 联调
======================================================================

现在执行“文件存储阶段 3：后端与 Cloudflare R2 真实联调”。

项目根目录：
/Applications/c2c游戏服务软件

前提：

- 阶段 1 已完成。
- 阶段 2 的开发 Bucket 和最小权限 Token 已创建。
- 只允许使用开发环境资源和无隐私测试文件。

配置并验证：

FILE_STORAGE_MODE=s3
FILE_STORAGE_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
FILE_STORAGE_REGION=auto
FILE_STORAGE_ACCESS_KEY_ID=<secret>
FILE_STORAGE_SECRET_ACCESS_KEY=<secret>
FILE_PUBLIC_BUCKET=xiongzai-dev-public-media
FILE_PRIVATE_BUCKET=xiongzai-dev-private-media
FILE_UPLOAD_URL_TTL_SECONDS=600
FILE_UPLOAD_SESSION_TTL_SECONDS=3600
FILE_DOWNLOAD_URL_TTL_SECONDS=300
FILE_UPLOAD_HOURLY_LIMIT=20

要求完成真实闭环：

1. 获取文件策略。
2. 申请 PRODUCT_IMAGE 上传凭证。
3. 使用预签名 PUT URL 上传自动生成的测试 PNG。
4. 原样发送全部签名请求头。
5. 调用完成确认。
6. 服务端从 R2 重新读取文件。
7. 校验大小、SHA-256、MIME 和图片尺寸。
8. 文件进入 VERIFIED + PENDING。
9. 管理员审核通过。
10. 验证公开访问。
11. 验证私有文件短时签名访问。
12. 验证所有权和管理员权限。
13. 验证篡改、错误 MIME、错误大小、错误哈希、过期 URL 和越权访问失败。
14. 验证删除后数据库状态和 R2 对象一致。
15. 清理本阶段创建的精确测试对象，不得清空 Bucket。

如果 SigV4、R2 元数据或 CORS 不兼容，应修复代码或最小化配置，不能关闭完整性检查。

运行文件存储测试、相关 API 集成测试和完整 API 回归。

完成后报告真实测试结果、修改文件、测试数量和剩余问题，然后停止，不自动进入阶段 4。

阶段 4：用户端 App 图片上传
======================================================================

现在执行“文件存储阶段 4：用户端 App 图片上传接入”。

项目根目录：
/Applications/c2c游戏服务软件

前提：后端与开发环境 Cloudflare R2 真实联调已经通过。

本阶段接入：

- USER_AVATAR
- SELLER_AVATAR
- SELLER_COVER
- PRODUCT_IMAGE

先检查 apps/mobile 的 API 客户端、鉴权、媒体选择、权限管理、错误处理和现有上传安全降级。

实现统一上传模块，不要把上传逻辑重复写进每个页面。

统一流程：

1. 查询服务端文件策略。
2. 请求系统相册或相机权限。
3. 选择图片。
4. 按业务用途裁剪。
5. 压缩并保留合理画质。
6. 读取实际文件大小。
7. 计算 SHA-256。
8. 申请上传凭证。
9. 使用预签名 PUT URL 直传 R2。
10. 显示真实上传进度。
11. 调用完成确认。
12. 展示服务端校验和审核状态。
13. 只保存服务端返回的 file_id。
14. 审核通过后才能绑定公开业务对象。

状态必须覆盖：

- 选择文件
- 裁剪预览
- 计算哈希
- 申请凭证
- 上传中
- 服务端校验中
- 审核中
- 审核通过
- 审核拒绝
- 上传失败
- URL 过期
- 网络断开
- 取消上传
- 重试

安全要求：

- R2 密钥不能进入 App。
- 本地 URI 不能作为服务端 URL。
- 不信任本地扩展名和 MIME。
- 403 或签名过期后重新申请凭证。
- App 重启后不能把未完成任务当成成功。
- 日志不得记录签名 URL、Token、手机号或敏感本地路径。
- 不使用真实用户资料测试。

接入头像、陪玩申请、封面和商品主图页面，补齐测试并运行 Mobile TypeScript、Lint、单元测试和相关 API 回归。

完成后报告修改文件、已接入页面、测试结果和剩余问题，然后停止，不自动进入阶段 5。

阶段 5：声音名片与投诉证据
======================================================================

现在执行“文件存储阶段 5：声音名片和私有投诉证据接入”。

项目根目录：
/Applications/c2c游戏服务软件

前提：阶段 4 的图片上传已经稳定通过。

本阶段接入：

1. VOICE_SAMPLE
2. COMPLAINT_EVIDENCE

声音名片要求：

- 支持录制或选择音频。
- 时长必须为 10–30 秒。
- 格式根据服务端策略选择 AAC、M4A 或 MP3。
- 上传前显示时长和大小。
- 支持试听、删除、重新录制、上传失败重试。
- 服务端计算的音频时长必须作为最终依据。
- 使用 SIGNED 受控访问，不直接公开原始对象。
- 审核通过前不能绑定陪玩公开主页。

投诉证据要求：

- 只允许 COMPLAINT_EVIDENCE 用途。
- 使用私有 Bucket。
- 只能由文件所有者和有权限管理员访问。
- 不生成永久公开 URL。
- 不允许使用头像或商品图片 file_id 冒充投诉证据。
- 显示上传、校验、审核、拒绝和重试状态。
- 投诉提交或补证时只能提交 VERIFIED 的证据 file_id。
- 不在日志、通知或公开页面泄漏证据 URL。

补充测试：

- 音频不足 10 秒和超过 30 秒
- 音频格式伪装
- 投诉证据越权
- 错误文件用途
- 私有文件匿名访问
- 签名 URL 过期
- 重复提交
- 删除已绑定证据
- 网络中断与重试

如果音频处理依赖缺失，应明确说明并安全阻断，不能伪造上传成功。

完成后运行 Mobile 和相关 API 回归，报告修改文件、测试结果和剩余风险，然后停止，不自动进入阶段 6。

阶段 6：恶意文件扫描与异步审核
======================================================================

现在执行“文件存储阶段 6：恶意文件扫描与异步审核”。

项目根目录：
/Applications/c2c游戏服务软件

先读取 docs/文件存储-V1.0.md，并检查现有上传、审核、Worker、Queue、Outbox 和数据库状态设计。

本阶段先完成供应商无关的扫描架构，不默认购买付费服务。

实现目标：

1. 定义可替换的 FileSafetyScanner 接口。
2. 将格式校验与恶意文件扫描明确区分。
3. 上传确认成功后进入等待扫描状态。
4. 扫描通过后才允许进入内容审核或 APPROVED。
5. 扫描发现风险时标记 REJECTED/FLAGGED 并阻断访问。
6. 扫描失败、超时或供应商不可用时保持安全关闭。
7. 支持幂等重试，不能重复审核或重复删除。
8. 记录扫描供应商、规则版本、扫描时间、结果和错误代码。
9. 不保存不必要的文件原文或敏感响应。
10. 管理员操作写入审计日志。

评估三类方案：

- 自建 ClamAV
- Cloudmersive 等商业扫描 API
- OPSWAT MetaDefender 等私有多引擎方案

禁止把用户隐私文件提交到公共 VirusTotal。

如果需要：

- 创建 Cloudflare Queue
- 配置 R2 Event Notification
- 部署 Worker
- 购买扫描服务
- 上传文件到第三方
- 新增付费资源

必须先说明费用、隐私影响、数据处理地区、保留策略、回滚方式并等待我授权。

在未获得付费授权时，可以完成接口、队列消费者、假扫描器和集成测试，但不能声称真实恶意文件扫描已上线。

完成后报告架构、修改文件、测试结果、供应商建议和仍需授权的事项，然后停止，不自动进入阶段 7。

阶段 7：CDN、生命周期与上线验收
======================================================================

现在执行“文件存储阶段 7：CDN、生命周期、监控与上线验收”。

项目根目录：
/Applications/c2c游戏服务软件

前提：开发环境上传、App 接入和扫描流程已经通过。

本阶段先完成上线审计和安全配置准备。任何生产资源、DNS、域名、证书或付费服务变更都必须先获得明确授权。

任务：

1. 为公开媒体设计 CDN 自定义域名，例如 assets.example.com。
2. 私有 Bucket 保持禁止匿名访问。
3. 为头像、封面和商品图片设计缓存策略。
4. 禁止列表页直接加载超大原图。
5. 规划缩略图、WebP/AVIF 转换和缓存失效。
6. 设计未完成上传、失败文件和孤儿对象的生命周期清理。
7. 实现或完善对象删除重试 Worker。
8. 增加上传成功率、确认失败率、扫描失败率、存储量和删除积压监控。
9. 增加密钥轮换、泄漏处置和最小权限检查。
10. 检查日志、审计、隐私和数据保留策略。
11. 制定开发、测试、预发布和生产环境隔离方案。
12. 执行完整后端、Mobile、数据库和用户全链路回归。
13. 编写回滚、故障降级和恢复演练文档。

禁止：

- 未授权修改 DNS
- 未授权绑定生产域名
- 未授权创建生产 Bucket
- 未授权发布应用
- 未授权上传真实用户数据
- 为通过验收关闭安全检查
- 把开发密钥复制到生产

最终报告必须区分：

1. 已完成且验证通过
2. 仅在开发环境验证
3. 等待生产授权
4. 仍阻断上线的事项
5. 外部资源及费用
6. 回滚方式
7. 修改文件
8. 所有测试的实际结果

完成本阶段后停止，不执行正式生产发布。
