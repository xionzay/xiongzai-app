# 文件存储阶段 3 完成报告 V1.0

日期：2026-08-21

## 1. 范围与结论

文件存储阶段 3 已完成 `USER_AVATAR` 的用户端 App 直传实现、状态与失败恢复、后端头像绑定约束、真实本地 MinIO + 隔离 PostgreSQL 全链路验证，以及 API/Mobile 回归。阶段范围严格停在用户头像，没有实现卖家头像、封面、商品图片、语音、投诉证据或管理员后台 UI。

## 2. 移动端模块结构

- `src/features/files/file-upload-domain.ts`：提供商无关的头像上传领域流程、状态、校验、错误分类、确认重试和审核通过后的资料绑定输入。
- `src/features/files/file-upload-api.ts`：读取本地字节、Expo Crypto SHA-256、文件策略/申请/确认/访问/删除 API 适配。
- `src/features/files/presigned-upload.ts`：仅负责原始预签名 PUT，不经过带 Bearer 的 API 客户端。
- `src/features/account/media-avatar-screen.tsx`：选择、1:1 裁剪、本地预览、上传、取消、确认重试、审核状态刷新、拒绝删除、审核通过绑定和正式头像展示。
- `src/types/api.ts`：文件策略、上传凭证、文件状态和响应类型。
- `tests/file-upload.test.ts` 与 `tests/media-avatar-screen.test.ts`：领域流程、传输安全与页面契约测试。

没有新增运行时依赖。已有 Expo Image Picker 与 Expo Crypto 被复用。

## 3. `USER_AVATAR` 全流程

1. 用户从相册选择或拍摄图片，系统编辑器按 1:1 裁剪；App 不请求 Base64 或 EXIF。
2. App 只在本地预览裁剪 URI，读取真实二进制后拒绝空文件、未知/不允许 MIME 和超出服务端策略大小的图片。
3. App 对同一字节数组计算 64 位小写十六进制 SHA-256。
4. App 用登录 Bearer 调用 `GET /files/policies` 和 `POST /files/uploads`，只申请 `USER_AVATAR`。
5. App 使用服务端返回的短时 URL 和指定请求头直接 PUT 同一份字节。PUT 不走 API 客户端、不添加 Authorization/Bearer，也不输出 URL、请求体或本地路径。
6. PUT 成功后调用 `POST /files/:fileId/complete`。后端 HEAD 并重新读取对象，核对大小、声明哈希、真实 MIME 和图片尺寸，成功后写为 `VERIFIED + PENDING`。
7. `PENDING` 时继续显示旧的正式头像；`REJECTED` 时不修改资料，可删除后重选；只有 `VERIFIED + APPROVED` 才可绑定。
8. 绑定前先刷新 `/me`，使用最新 `user.version` 与 `profile.version` 更新 `avatar_file_id`；并发冲突会再次刷新本地用户事实，不覆盖其他设备更新。
9. 个人资料的正式头像通过公共文件读取组件展示，本地 URI 永远不会写成服务端头像。

## 4. 状态、取消与重试

状态机包含：`idle`、`reading`、`hashing`、`requesting`、`uploading`、`confirming`、`pending_review`、`approved`、`rejected`、`binding`、`bound`、`cancelled`、`failed`。

- 页面卸载会中止进行中的读取/API/PUT/确认请求，并以 mounted guard 阻止卸载后的状态更新。
- 进行中的上传由单一 AbortController 管理，重复点击不会产生第二条上传链。
- PUT 失败前可以清理尚未成功上传的待上传记录。
- PUT 已成功但 `complete` 暂时失败或被取消时，保留文件 ID，只显示“只重试服务端确认”，不得重复上传字节。
- 服务端哈希、大小或格式校验失败不会伪装成网络故障，也不会自动再次 PUT。
- 当前不显示虚假的上传百分比；只显示真实阶段。若未来需要字节进度，须引入可观测的原生传输实现并单独评审。

## 5. API 与所有权边界

本次 App 使用的接口为：

- `GET /api/v1/files/policies`
- `POST /api/v1/files/uploads`
- `POST /api/v1/files/:fileId/complete`
- `GET /api/v1/files/:fileId/access`
- `DELETE /api/v1/files/:fileId`
- `GET /api/v1/files/:fileId`
- `GET /api/v1/me`
- `PATCH /api/v1/me/profile`

除预签名 PUT 外，用户 API 使用登录 Bearer 并由后端强制所有权。预签名 PUT 只具备短时、单对象、指定方法和绑定元数据的能力。文件响应不会暴露 Bucket、`object_key`、存储密钥或数据库连接信息。

## 6. 真实本地验证

审计时 MinIO 正在运行，仅监听 `127.0.0.1:9000`（以及 IPv6 回环）和控制台 `127.0.0.1:9001`，没有局域网或公网监听。三个本地 Bucket 均存在且禁止匿名访问：

- `xiongzai-dev-quarantine-media`
- `xiongzai-dev-public-media`
- `xiongzai-dev-private-media`

quarantine Bucket 的 CORS 仍只允许文档列出的本地 Web Origin；原生 App 不依赖 CORS。本次真实验证结果：预签名 PUT/GET、HEAD、服务端读取、quarantine→public、quarantine→private、精确删除、SHA-256/真实 MIME/图片尺寸、允许 Origin、不可信 Origin 拒绝、匿名对象访问拒绝均通过，验证对象在 `finally` 中清理。

另有一条 `USER_AVATAR` 集成测试使用合成的无隐私 PNG，完成：用户申请 → 真实 MinIO PUT → 服务端确认 → `VERIFIED + PENDING` → 所有者访问 → 管理员批准 → public Bucket → 刷新最新用户版本 → 绑定头像 → 公共读取并复核哈希 → 精确清理最终对象。测试使用独立临时 PostgreSQL Schema，并在结束后清理。

这不是实体手机手工点击/裁剪测试。MinIO 没有为真机改成局域网监听；实体手机的 `127.0.0.1` 指向手机自身。任何真机局域网方案必须另行授权。
