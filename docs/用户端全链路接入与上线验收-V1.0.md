## 4. 数据一致性与事务结论

- 创建订单、履约状态切换、支付、退款、财务和通知事件均由业务事务同步写入 Outbox。
- `client_message_id`、订单/支付/提现幂等键和渠道事件标识可阻止重复业务副作用。
- E2E 查询所有 `POSTED` 账务事务，未发现借贷不平或分录不足两条的事务。
- 完成订单只生成一条主收益；提现后退款生成新欠款，不修改历史提现或账务分录。
- 用户端与后台读取同一订单时，主键、订单号、订单状态、支付状态和累计退款金额一致。
- E2E 使用临时 Schema；测试数据不会写入开发业务表或生产环境。

## 5. 安全与敏感信息检查

- Access/Refresh Token 使用 HttpOnly Cookie；用户端未把 Token 写入 `localStorage`。
- 手机号、姓名、证件和收款信息由应用层密文、HMAC 查询哈希和脱敏值承载。
- 自动化日志断言确认测试手机号和短信验证码未出现在日志中。
- 验收时发现并移除了管理后台登录框预填的演示账号和密码，并添加回归断言防止恢复。
- 生产配置会拒绝 development 短信 Provider、Mock 支付、Mock 打款和日志型 Event Publisher。
- 支付与打款回调需要签名并依赖唯一事件标识实现幂等。
- 管理端财务、审核、RBAC 和聊天取证权限由服务端校验，前端不直接访问数据库。

## 6. 索引与慢查询检查

在 PostgreSQL 16 上使用 `EXPLAIN (FORMAT JSON)` 验证以下核心查询能够使用预期索引：

- `orders_buyer_created_idx`
- `orders_seller_created_idx`
- `messages_conversation_created_idx`
- `notifications_user_unread_idx`
- `outbox_events_dispatch_idx`
- `scheduled_jobs_dispatch_idx`

当前开发核心业务表为空，因此本次结果只能证明索引路径可用，不能代表生产数据规模下的真实 P95/P99。上线前必须用脱敏的生产等量级数据完成压测，并复核慢查询日志、锁等待、连接池饱和度和游标分页性能。

## 7. 部署变量清单

真实值必须进入部署平台 Secret Manager，不得提交到 Git 或输出到日志。

### API

- 环境与数据库：`NODE_ENV`、`DATABASE_URL`、`DATABASE_MAX_CONNECTIONS`、`DATABASE_CONNECTION_TIMEOUT_MS`
- 监听与跨域：`API_HOST`、`API_PORT`、`API_CORS_ORIGINS`
- Token：`TOKEN_ISSUER`、`USER_TOKEN_AUDIENCE`、`ADMIN_TOKEN_AUDIENCE`、`INTERNAL_TOKEN_AUDIENCE`
- 密钥：`USER_TOKEN_SECRET`、`ADMIN_TOKEN_SECRET`、`INTERNAL_TOKEN_SECRET`、`CURSOR_SIGNING_SECRET`
- 敏感数据：`PII_ENCRYPTION_KEY`、`PII_HMAC_KEY`、`AUTH_HMAC_KEY`
- 会话与短信：`ACCESS_TOKEN_TTL_SECONDS`、`REFRESH_TOKEN_TTL_SECONDS`、`SMS_PROVIDER_MODE`、`SMS_CODE_TTL_SECONDS`、`SMS_MAX_ATTEMPTS`、`SMS_MINIMUM_INTERVAL_SECONDS`
- 支付和打款：`PAYMENT_PROVIDER_MODE`、`PAYMENT_WEBHOOK_SECRET`、`PAYOUT_PROVIDER_MODE`、`PAYOUT_WEBHOOK_SECRET`

### Worker 与 Scheduler

- Worker：`WORKER_ID`、`WORKER_BATCH_SIZE`、`WORKER_POLL_INTERVAL_MS`、`EVENT_PUBLISHER_MODE`
- Scheduler：`SCHEDULER_ID`、`SCHEDULER_BATCH_SIZE`、`SCHEDULER_POLL_INTERVAL_MS`

### 网关与前端

- 用户端、后台和 API 必须使用 HTTPS。
- 网关将 `/api/v1`、`/admin-api/v1` 和 `/callbacks/v1` 转发到 API，并保留可信代理头。
- Cookie 的 Secure、HttpOnly、SameSite、Domain 和 Path 按正式域名确认。
- 配置静态资源/CDN、对象存储、CSP、HSTS、请求体上限和上传文件扫描策略。

## 8. 发布、迁移与回滚

### 发布顺序

1. 冻结迁移文件并完成数据库快照、恢复演练和发布审批。
2. 在预发布环境依次执行 `0000_initial_schema.sql`、`0001_core_invariants.sql`，再执行 `pnpm db:check` 和数据库验证。
3. 部署 API，确认 `/health/live` 与 `/health/ready` 返回 200。
4. 部署 Scheduler，再部署 Worker；观察 Outbox、Inbox 和 scheduled job 积压。
5. 部署管理后台和用户端，执行冒烟测试及本文件第 3 节的 E2E。
6. 小流量开放，观察错误率、慢查询、支付回调、账务平衡和告警后再逐步放量。
7. 生产迁移不运行测试 Seed，不执行 Mock 支付、短信或打款端点。

### 回滚原则

1. 先停止入口写流量、Scheduler 和 Worker，保留只读诊断能力。
2. 应用发布失败时回滚到兼容当前 Schema 的上一应用版本。
3. 迁移坚持向前修复，不手工删除订单、支付、退款、审核、审计或账务记录。
4. 若数据库发生不可向前修复的严重问题，使用发布前已验证快照恢复到新数据库实例，完成一致性检查后切换 `DATABASE_URL`。
5. 支付、退款、提现和 Outbox 在恢复后按外部事件号及幂等键重放；先对账再恢复写流量。
